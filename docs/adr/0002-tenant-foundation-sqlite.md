# ADR 0002: Fondasi tenant di SQLite

Tanggal: 18 November 2026 (Asia/Jakarta). Status: diterima untuk T01; aktivasi multi-tenant belum tersedia.

Review lanjutan sebelum T02: startup kini hanya menerima `schema_migrations.version=1` dengan fingerprint yang cocok. Default `ALLOW_AUTO_MIGRATE=0`; operator menjalankan `ALLOW_AUTO_MIGRATE=1 node scripts/migrate-schema.mjs` pada maintenance window. Versi yang tidak memiliki migrasi terdaftar tetap ditolak meski flag aktif. Legacy bootstrap dibekukan di legacySchema.js dan hanya berjalan dalam transaksi migrasi IMMEDIATE yang sama dengan rebuild tenant dan pencatatan versi. Snapshot dibuat sebelum transaksi; fingerprint diperiksa lagi sesudah lock didapat untuk menolak perubahan saat menunggu. Database T01 lama yang belum mempunyai schema_migrations dapat diadopsi secara eksplisit dengan flag yang sama.

Fingerprint SHA-256 berasal dari nama tabel dan atribut kolom (nama, tipe, nullability, default, posisi primary key), dengan tabel/kolom diurutkan secara kanonis; urutan fisik kolom bukan perbedaan semantik. Hash yang diterima dibekukan di src/schema-fingerprints.json, dibangun dari bootstrap kode yang direview, bukan belajar dari database runtime. Skema kosong, legacy lengkap, legacy sebelum registri media, dan T01 terdahulu dikenali. Penambahan/penghapusan/perubahan kolom atau tabel yang tidak terdaftar menolak startup sebelum bootstrap. Fingerprint ini bukan checksum trigger/index; trigger diuji tersendiri pada trigger-matrix.md.

Owner default ditentukan dalam migrasi dengan ORDER BY prioritas role admin lalu id ASC LIMIT 1; bila tak ada admin, user id terkecil. ID pilihan dicatat sebagai defaultOwnerId di report_json tenant_migrations. Bootstrap kosong membuat admin terlebih dahulu dalam transaksi yang sama. Ini tidak mengangkat owner menjadi platform admin. Backup kini satu snapshot pre-bootstrap/pre-T01 per run runner; retensi MIGRATION_BACKUP_KEEP (default 5, minimum 1), nama UUID, jumlah dan total byte dilaporkan setelah migrasi. Pola **/migration-backups/ diabaikan Git untuk seluruh DATA_DIR. Keterangan dua snapshot/tanpa retensi di bagian historis ADR berikut digantikan oleh keputusan review ini.

SQLite WAL dipertahankan. SQLite tidak menyediakan row-level security (RLS), sehingga isolasi berikutnya wajib ditegakkan pada lapisan data, resolver request, worker, socket, direktori, dan suite kebocoran. Kolom tenant saja tidak menjamin isolasi.

Identitas user bersifat global. `tenant_members(tenant_id,user_id)` memetakan banyak user ke banyak tenant dengan role `owner`, `tenant_admin`, atau `agent`. Partial unique index membatasi maksimal satu owner per tenant. Migrasi memilih admin lama dengan ID terkecil sebagai owner default (fallback user ber-ID terkecil), dan memetakan user lama lainnya menjadi tenant_admin/agent. Onboarding/transfer owner harus menjamin tepat satu owner dalam transaksi pada T04/T11; index sendiri tidak mencegah tenant tanpa owner. Role global lama dipertahankan untuk kompatibilitas; pemisahan `platform_role` dilakukan pada T04. Platform admin tidak mendapatkan bypass pada resolver.

Seluruh 21 tabel resource dalam `TENANT_TABLES` mendapat FK `tenant_id`, indeks tenant, dan NOT NULL fisik. `users` global; `sessions` global dengan `active_tenant_id` nullable untuk sesi tanpa tenant; `meta` hanya menyimpan penanda migrasi/backup global yang sudah ada; `tenant_migrations` menyimpan laporan migrasi operasional. Konfigurasi tenant baru tidak boleh ditaruh di `meta`. Kontak lama yang menjadi arsip tetap diberi tenant. Path media/auth dan antrean belum dipartisi di T01; registri media hanya mendapat tenant tanpa mengubah URL/path.

Kunci alami phone, label name, SKU, order code, contact JID arsip, serta AI seen ID menjadi unik dalam tenant. ID numerik resource tetap global untuk menjaga relasi dan dedupe `(number_id,wa_id)`. Trigger memeriksa kesamaan tenant pada FK antar-resource dan relasi contacts_v2/number; tenant_id resource tidak bisa diubah melalui UPDATE biasa. Validasi user assignee/owner dan seluruh otorisasi mutasi tetap pekerjaan T06.

`resolveTenantScope(req)` membaca cookie session dari database, memeriksa masa berlaku, mencocokkan principal yang sudah terautentikasi bila tersedia, membaca active tenant server-side, lalu memvalidasi ulang membership dan status tenant setiap pemanggilan. Nilai tenant_id dari body/query/params hanya boleh cocok dengan tenant tersebut. Tidak ada cache membership dan tidak ada pengecualian role admin. Resolver mengembalikan scope immutable atau error 401/403. Resource asing nanti harus dijawab 404 oleh query berscope (T05/T06). Middleware disiapkan dengan marker `tenantScoped`; pemasangan dan inventaris seluruh rute adalah T02/T03.

Migrasi berjalan sebelum server/worker diaktifkan. Backup SQLite API mencakup WAL: snapshot pertama sebelum bootstrap skema lama, snapshot kedua sebelum transaksi T01. Kedua snapshot disimpan di `DATA_DIR/migration-backups/pre-t01-<random UUID>.sqlite`. Startup pada database baru juga memakai prosedur yang sama. Operator harus menghentikan instance lain saat migrasi: transaksi IMMEDIATE mengunci penulis selama backfill/rebuild, tetapi snapshot dibuat sebelum lock dan bukan mekanisme koordinasi multi-host. Backup berisi data sensitif, harus mengikuti ACL direktori data; chmod bukan pengganti ACL Windows. Snapshot tidak dipangkas otomatis.

Transaksi migrasi: expand nullable → buat tenant default/membership → backfill → verifikasi nol NULL → rebuild NOT NULL/FK → pulihkan indeks, trigger lama, dan high-water mark AUTOINCREMENT → periksa jumlah baris dan foreign_key_check → simpan marker T01. FK dimatikan hanya selama rebuild pada koneksi migrasi dan dikembalikan dalam finally; kegagalan membatalkan transaksi. Jangan mengedit sqlite_master melalui writable_schema. Migrasi ulang yang memiliki marker bersifat no-op.

`MULTITENANT_ENABLED` default `0`. Dengan flag mati, writer lama tetap dapat menulis ke default melalui `DEFAULT 'default'`; ini hanya jembatan kompatibilitas. Saat flag `1`, T01 sengaja menggagalkan startup sebelum database dibuka: query, worker, dan socket lama belum aman bagi banyak tenant. Guard baru boleh dilepas setelah tahap isolasi dan gate kebocoran selesai; pada saat itu writer harus memberikan tenant secara eksplisit, dan default kolom harus dicabut atau dilindungi. Mematikan flag mempertahankan skema dan mode lama, bukan menghapus data tenant.

Pindah ke Postgres + RLS sebelum salah satu kondisi terjadi: **lebih dari 25 tenant**, **lebih dari satu host/penulis**, atau **kebutuhan audit/kebijakan isolasi di SQL**. Lock contention yang mengganggu target latensi, kebutuhan HA/replica, dan ukuran backup yang melewati jendela pemulihan juga memicu evaluasi lebih awal. RLS harus memakai tenant dari konteks transaksi server, tanpa role aplikasi BYPASSRLS; migrasi memerlukan uji kesetaraan data dan suite kebocoran yang sama.

Rollback operasional T01: set flag 0. Rollback skema hanya saat semua proses berhenti, dengan merestore snapshot pertama dan kode baseline; karantina database/WAL/SHM saat ini sebelum restore agar WAL baru tidak diaplikasikan ke snapshot lama. Backup pertama dapat kehilangan perubahan setelah waktu snapshot; karena itu rollback skema memerlukan maintenance window dan rekonsiliasi. Tidak ada down-migration yang membuang tenant secara otomatis.
